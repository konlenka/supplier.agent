## Findings, ranked

| # | Where (on `main`) | What goes wrong for the café | Status |
|---|---|---|---|
| 1 | `app.py` `/trigger` | Anyone who has the URL and the key — which is in the public code — can make the bot text a real order to the supplier, as many times as they like. | **Fixed in code.** Key comes from `TRIGGER_KEY`; unset means the URL is off. **Still to do: set `TRIGGER_KEY` in Railway before deploying**, and check whether the GitHub repo is public. |
| 2 | `app.py` `run_weekly_order` | Nothing stopped the same order being sent twice: a restart, the trigger URL, a retry. | **Fixed.** One order per order week (Wed–Tue), logged in a new `job_runs` table. `force=1` overrides, but not within 10 minutes of the last send. |
| 3 | `app.py` + `ordering_agent.py` | The quantities came straight from a model with no limit in code and no person checking. A wrong number went to the supplier as sent. It could also order nothing while stock was short, and staff were told "stock levels are good". | **Fixed.** The stock arithmetic is the ceiling; the model can trim, not inflate, and not cancel. Malformed orders are sent back to it. |
| 4 | `app.py` `date.today()` | On a UTC host, 9am Wednesday in Melbourne is still Tuesday. The order text carried Tuesday's date and the public-holiday window was a day out. Depends on the host's timezone, which I have not checked on Railway. | **Fixed.** Uses the Melbourne date. |
| 5 | `stock_parser.py`, `storage.py` | Any staff text counted as a fresh stock report — "thanks" included — and the model's output was saved unchecked. Freshness was judged on the last message, not per item, so one item counted this week hid month-old counts of the others; an item never counted was read as zero and re-ordered in full. | **Fixed.** Output is validated; empty or odd parses are rejected; freshness is per item. |
| 6 | `app.py` stale path | When the count was stale, the job texted staff and stopped. Staff sent the count; no order went out that week unless someone hit the trigger URL. | **Fixed.** The count that completes the set releases the order, and the reply says so; a partial count gets a reply naming what is still missing. |
| 7 | `app.py` | A failed supplier SMS crashed the job with nobody told. One bad staff number stopped the rest getting their text. | **Fixed.** Staff are texted. A send that errors is reported as "may not have reached the supplier — check first", because an error after the SMS provider accepted the message looks identical; that is never re-sent automatically. |
| 8 | `app.py` staff summary | Lactose free and coconut are counted in bottles but the "total inventory" line showed them in boxes, rounded down: 7 bottles read as 0. | **Fixed.** Bottle items are shown in bottles. |

Also fixed: a run missed because the process was restarting at 9:00 is caught up on startup; the
scheduler no longer drops a run that starts more than one second late.

## Independent review

A separate QA review of the first version of this diff found four problems, all since fixed and
tested: an order released late on a Friday cancelled the next Wednesday's (the guard counted days,
not weeks); the "order goes out once the count is in" promise could fail silently; "nothing was sent"
was asserted when the code couldn't know; and the model could zero an order. **The fixes for those
four have not themselves been re-reviewed** — that is the next step before merge.

## Decisions for Christian

- **First Wednesday after deploy:** staleness is now per item. If production has an item nobody has
  counted lately (the local database has no coconut row), the first run will hold the order and ask for
  it, where `main` would have ordered. Warn staff, or check production `current_stock` first.
- **Staff-facing wording changed** in four texts (stale request, partial-count reply, failure, summary
  units). Read them in `app.py` before they go to the café.
- **Is the model step worth keeping?** The arithmetic now decides the ceiling and the floor. The model
  can only trim an order using history. A rule would do that with no API call and nothing to go wrong.
- **Approval for the first runs** (build protocol §8.5) and **an off switch staff can use** (§8.4) don't
  exist. Both fit SMS: "reply YES to send", and a PAUSE / RESUME text.

## Later (not fixed, one line each)

- The once-a-week guard lives in one process and one SQLite file. If `data/` is not on a persistent Railway volume, every redeploy wipes stock, order history and the guard. Confirm in Railway.
- The scheduler only starts under `python app.py`. Confirm that is Railway's start command.
- `/trigger` is still a GET with the key allowed in the URL, so it lands in logs and browser history.
- The failure text goes out through Twilio, the same channel that may be down. No second channel.
- A count that completes the set sends the order within seconds; a typo has no correction window (bounded by the cap).
- Staff and supplier phone numbers are written to Railway logs.
- Dependencies are unpinned (`>=`), so a redeploy can pull a new major version.
- `dry_run.py` says nothing is sent but writes sample stock into whatever database it points at.
- The supplier's first name is hardcoded in the order text.
- README setup step 1 has a placeholder clone URL.
